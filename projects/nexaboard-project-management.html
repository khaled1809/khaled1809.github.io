NexaBoard — Gestion de projets et tâches collaborative

Une plateforme de travail d’équipe permettant d’administrer des projets, organiser les tâches dans un Kanban, collaborer par commentaires et piloter l’avancement à partir d’indicateurs adaptés aux droits de chaque utilisateur.

Contexte

Le besoin à résoudre

Le projet devait ressembler à un véritable outil interne d’entreprise, et non à une simple liste de tâches. Une équipe doit pouvoir créer des projets privés, attribuer un manager, ajouter des membres, déplacer des tâches entre trois colonnes, commenter le travail et suivre les retards sans exposer les données d’autres équipes. Les difficultés principales concernaient le cycle de vie sécurisé des JWT dans une SPA, les permissions à la fois globales et propres à chaque projet, la cohérence de l’ordre du Kanban lors de déplacements concurrents, la synchronisation entre manager et membres, le calcul d’indicateurs limités au périmètre accessible et la reproductibilité du déploiement.

Approche

La solution mise en place

J’ai organisé NexaBoard en monorepo avec une SPA Vue.js 3 écrite en TypeScript, des stores Pinia, Vue Router, Tailwind CSS 4, Chart.js et vuedraggable, puis une API Python fondée sur Django 5.2 et Django REST Framework. Le modèle utilisateur étend AbstractUser, utilise l’e-mail comme identifiant et distingue les rôles ADMIN, MANAGER et MEMBER. L’access token reste en mémoire dans le navigateur ; le refresh token est placé dans un cookie HttpOnly, renouvelé par rotation et ajouté à la liste noire après usage avec SimpleJWT. Axios centralise le Bearer token et rejoue une requête après un 401 grâce à une promesse de refresh partagée. Côté métier, Project, ProjectMembership, Task, Comment et Activity sont persistés avec le Django ORM dans PostgreSQL 17. Le déplacement Kanban appelle une action REST qui utilise transaction.atomic, select_for_update et bulk_update pour verrouiller puis renuméroter les colonnes source et cible. L’interface applique une mise à jour optimiste et effectue un rollback si l’API échoue. Le dashboard agrège les projets visibles, les tâches terminées, en cours ou en retard, les priorités, les prochaines échéances et l’activité récente, puis affiche la répartition avec Chart.js. drf-spectacular produit Swagger / OpenAPI ; Docker Compose orchestre PostgreSQL, Gunicorn et Nginx ; GitHub Actions décrit les contrôles backend et frontend. L’archive contient 8 tests Django et 3 tests Vitest. Dans l’environnement de génération, les 43 fichiers Python et les 43 fichiers TypeScript/Vue ont été soumis à des contrôles statiques, mais les tests d’exécution, l’installation des dépendances, le build Vite et le démarrage Docker sont restés non exécutés faute d’accès aux registres et de moteur Docker.

Architecture

Comment le projet est structuré

01

SPA Vue 3 typée et composants réutilisables

L’interface utilise la Composition API avec <script setup>, TypeScript, Vue Router et Tailwind CSS 4. Les écrans d’authentification, de dashboard, de projets, de profil et d’équipe s’appuient sur des composants communs pour les boutons, modales, badges, avatars, barres de progression et états vides.

02

État applicatif Pinia et couche HTTP centralisée

Les stores auth, projects, tasks, dashboard et ui séparent les responsabilités. Axios ajoute l’access token conservé en mémoire, intercepte les réponses 401 et partage une unique refreshPromise afin d’éviter plusieurs rotations simultanées quand plusieurs requêtes expirent au même moment.

03

Authentification Django et cycle JWT

Le modèle User étend AbstractUser, impose un e-mail unique et ajoute le rôle métier. Les endpoints d’inscription, connexion, refresh, déconnexion, profil et mot de passe oublié utilisent SimpleJWT, les validateurs Django et un refresh token en cookie HttpOnly avec rotation et liste noire.

04

Domaine collaboratif modélisé explicitement

Project porte le calendrier, le statut, la couleur, le créateur et le manager. ProjectMembership matérialise l’appartenance et son rôle. Task stocke priorité, statut, position, échéance et assignation ; Comment conserve les échanges ; Activity forme un journal fonctionnel des créations, modifications et déplacements.

05

Permissions objet et querysets cloisonnés

Les querysets ne renvoient que les projets gérés ou rejoints par l’utilisateur, sauf pour l’administrateur. ProjectPermission, TaskPermission et CommentPermission distinguent consultation, gestion du projet, travail sur les tâches, suppression par le créateur ou le manager et édition d’un commentaire par son auteur.

06

Kanban transactionnel et interface optimiste

vuedraggable manipule localement les colonnes TODO, IN_PROGRESS et DONE, puis appelle /tasks/{id}/move/. L’API exécute transaction.atomic, verrouille les lignes avec select_for_update, insère la tâche à la position demandée, normalise les deux colonnes et enregistre l’activité. Le store restaure son état précédent par rollback en cas d’erreur.

07

Dashboard consolidé selon le rôle

L’API calcule uniquement sur les projets accessibles : volume de projets, tâches terminées, en cours et en retard, taux de réalisation, répartition par statut et priorité, progression des projets, échéances proches et activité récente. Vue affiche ces données avec des cartes, une liste de progression et un doughnut Chart.js.

08

Documentation, conteneurs et intégration continue

drf-spectacular expose le schéma OpenAPI et Swagger, tandis qu’une collection Postman documente les parcours. Docker Compose relie PostgreSQL 17, le backend Gunicorn et le frontend Nginx avec healthchecks. GitHub Actions prévoit check Django, contrôle des migrations, tests, Vitest et build Vite.

Résolution de problèmes

Difficultés rencontrées et décisions prises

Les points ci-dessous donnent de la visibilité sur le raisonnement technique, pas seulement sur les fonctionnalités finales.

Difficulté 1

Sécuriser une session JWT sans localStorage

Conserver les deux jetons dans le stockage JavaScript faciliterait leur exfiltration en cas de faille XSS, alors qu’un cookie seul ne suffit pas pour renseigner l’en-tête Authorization de l’API.

Approche retenue

L’access token court reste uniquement en mémoire et Axios l’ajoute au Bearer token. Le refresh token est inaccessible à JavaScript dans un cookie HttpOnly limité au chemin /api/auth/. SimpleJWT active la rotation et la liste noire ; la déconnexion révoque le refresh. Une refreshPromise partagée évite les courses entre plusieurs réponses 401.

Difficulté 2

Appliquer les rôles sans faire confiance au frontend

Masquer un bouton dans Vue ne protège pas l’API. Il fallait combiner les rôles ADMIN, MANAGER et MEMBER avec l’appartenance réelle à chaque projet.

Approche retenue

Les querysets sont filtrés avant même la permission objet, ce qui transforme un projet étranger en ressource introuvable. Les classes ProjectPermission, TaskPermission et CommentPermission réévaluent ensuite chaque opération. Le frontend adapte l’interface, mais Django REST Framework reste l’unique source de vérité.

Difficulté 3

Préserver un ordre Kanban cohérent

Deux déplacements rapprochés peuvent créer des positions dupliquées, des trous ou une tâche présente dans le mauvais ordre si les colonnes sont mises à jour par écritures indépendantes.

Approche retenue

L’action move s’exécute dans transaction.atomic, verrouille avec select_for_update les tâches de la colonne cible puis, si nécessaire, de l’ancienne colonne. Elle insère la tâche, renumérote toutes les positions et utilise bulk_update. Le client reste fluide grâce à une mise à jour optimiste et déclenche un rollback vers la copie précédente lorsque l’appel échoue.

Difficulté 4

Synchroniser manager et membres du projet

Le manager doit toujours appartenir au projet, ne doit pas pouvoir être retiré et un changement de manager doit rétrograder proprement l’ancien responsable sans créer de doublon d’appartenance.

Approche retenue

ProjectMembership possède une contrainte d’unicité sur project et user. Le serializer centralise la synchronisation dans _sync_members, ajoute systématiquement le manager et met à jour les rôles. Les actions d’administration refusent explicitement le retrait du manager courant.

Difficulté 5

Empêcher l’assignation d’une tâche à un tiers

Un identifiant utilisateur valide ne signifie pas que cette personne appartient à l’équipe du projet, et une API permissive pourrait divulguer ou attribuer du travail en dehors du périmètre autorisé.

Approche retenue

TaskSerializer valide le projet accessible et vérifie que l’utilisateur assigné est le manager ou un membre. Les tests fournis couvrent le rejet d’un outsider, tandis que les filtres de tâches restent limités aux projets visibles par la session.

Difficulté 6

Calculer des indicateurs sans fuite inter-équipe

Un dashboard global construit directement sur toutes les tâches révélerait des volumes, échéances ou activités appartenant à d’autres projets.

Approche retenue

DashboardView commence par le queryset projects_for(user), puis dérive toutes les agrégations depuis ce périmètre. Les retards excluent les tâches DONE, le taux de réalisation gère le cas sans tâche et les graphiques Chart.js reçoivent une structure déjà normalisée par l’API.

Difficulté 7

Réinitialiser un mot de passe sans révéler les comptes

Une réponse différente selon l’existence d’une adresse permettrait l’énumération des utilisateurs, et un token artisanal serait difficile à invalider correctement.

Approche retenue

L’endpoint renvoie une réponse générique, utilise default_token_generator lié à l’état du mot de passe et encode l’identifiant avec urlsafe_base64. En développement, le lien passe par le backend e-mail console ; en production, la documentation impose SMTP et RETURN_RESET_TOKEN=false.

Difficulté 8

Rendre la livraison reproductible et vérifiable

Le frontend, l’API et PostgreSQL nécessitent des versions, des dépendances et un ordre de démarrage cohérents, tandis que le dépôt doit rester contrôlable à chaque modification.

Approche retenue

Docker Compose définit le volume PostgreSQL, les healthchecks et les dépendances ; Nginx sert la SPA et reverse-proxy /api ; Gunicorn exécute Django. La CI GitHub Actions prévoit 8 tests Django, 3 tests Vitest, le contrôle des migrations et le build. Ces tests sont présents dans l’archive mais sont restés non exécutés ici, car l’installation des dépendances et Docker étaient indisponibles ; seuls les contrôles statiques ont été rejoués.

Progression

Ce que j’ai appris

Des acquis réutilisables dans d’autres projets et dans un contexte professionnel.

  • Construire une SPA Vue.js 3 avec Composition API, TypeScript, routage protégé et composants d’interface réutilisables.

  • Organiser l’état client avec Pinia et une couche de services REST typée plutôt que de disperser les appels HTTP dans les vues.

  • Concevoir un renouvellement JWT automatique avec access token en mémoire, refresh cookie HttpOnly, rotation, liste noire et reprise contrôlée après 401.

  • Modéliser les responsabilités métier avec Project, ProjectMembership, Task, Comment et Activity, ainsi que des contraintes et index adaptés.

  • Mettre en œuvre des permissions DRF globales et objet, puis limiter les querysets pour éviter toute fuite de données entre équipes.

  • Garantir la cohérence d’un drag & drop Kanban avec transaction.atomic, select_for_update, bulk_update et normalisation des positions.

  • Combiner mise à jour optimiste côté client et rollback pour conserver une interface réactive sans masquer les échecs serveur.

  • Produire des indicateurs opérationnels avec le Django ORM et les présenter dans Chart.js sans déplacer la logique d’autorisation dans le navigateur.

  • Documenter une API avec drf-spectacular, Swagger / OpenAPI et Postman afin de rendre les contrats testables par une autre équipe.

  • Préparer une livraison multi-conteneurs avec PostgreSQL, Gunicorn, Nginx, healthchecks et une CI GitHub Actions séparant backend et frontend.

Prise de recul

Ce que j’améliorerais dans une prochaine version

  1. Exécuter la pile complète sur une machine connectée, figer les lockfiles puis publier les sorties réelles des 8 tests Django, 3 tests Vitest, du build Vite et du contrôle OpenAPI.
  2. Ajouter des tests end-to-end Playwright couvrant inscription, refresh de session, permissions, création de projet, drag & drop, commentaires et dashboard.
  3. Tester les déplacements concurrents sur PostgreSQL et renforcer la stratégie de verrouillage pour les scénarios de forte activité sur une même colonne.
  4. Ajouter des notifications temps réel avec WebSocket ou Server-Sent Events pour les commentaires, assignations et changements de statut.
  5. Introduire Celery et Redis pour les rappels d’échéance, les e-mails et les traitements asynchrones, avec suivi des erreurs et reprises.
  6. Étendre le modèle vers des espaces de travail multi-organisations avec invitations, rôles d’organisation et isolation tenant par tenant.
  7. Ajouter les pièces jointes sur un stockage objet, une recherche PostgreSQL, des exports CSV et un calendrier de charge.
  8. Déployer une démonstration HTTPS, ajouter des captures réelles et remplacer le lien temporaire vers le profil GitHub par l’URL exacte du dépôt NexaBoard.
